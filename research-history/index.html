Timeline

從長菜單，到決策工作流，再回到閱讀尺度

每張卡都使用同一套問題：它處理了什麼、又把負擔搬到哪裡。舊 prototype 不會被事後美化，否則就無法理解它為什麼被拒絕。

01 · BASELINE

Complete menu

Accepted substrate

完整長頁、分類跳轉與 inline detail，建立可信的完整性與返回位置。

  • 保留：完整結構、inline detail、focus／scroll continuity
  • 未解：長頁線性、跨分類比較與全貌

02 · EXPERIMENT

Relational reading

Rejected as main flow

透過 Anchor 與 semantic axis，把六道分享料理投影成相對差異。

  • 保留：shared columns、truthful evidence
  • 失敗：必須先理解基準與比較軸，排版問題變成查詢操作
開啟 Prototype C
03 · WORKFLOW

Candidate workspace

Rejected as default flow

讓使用者在購物車之前保存幾道「認真考慮」的料理。

  • 保留：identity-only state、可逆性、return context
  • 失敗：把短期考慮變成清單管理
開啟流程快照
04 · WORKFLOW

Bounded comparison

Product-invalid

Candidate 之外再建立 2–3 道的比較 membership，技術上嚴謹但流程重複。

  • 保留：bounded projection、canonical order
  • 失敗：加入考慮後仍須逐道再按一次比較
在同一快照體驗
05 · PARTIAL

Ledger document

Useful partial solution

以 30 道密集分類段落、欄位對齊和 inline detail 取代商品卡與比較按鈕。

  • 保留：row grammar、alignment、同分類掃描
  • 未解：仍是一條更漂亮的長頁

06 · CURRENT HYPOTHESIS

Multi-scale menu map

Active hypothesis

完整結構始終可見，內容依全店、分類與料理三個閱讀尺度展開。

  • 嘗試：全貌、地標、局部閱讀與空間記憶
  • 尚未證明：展開成本是否低於長頁成本

Archive rules

怎麼閱讀這些快照

同一份內容

五個快照使用同一餐廳與同一批代表料理；新補的 Relational 與 Ledger 直接共用研究 fixture。

忠實保留缺點

Relational 從未選 Anchor 開始；Candidate 保留再次比較選取；Ledger 永久展開 30 道料理。

不是產品 fallback

快照是封閉的 HTML／CSS／原生 JavaScript 研究證據，不共用正式 app state，也不保存資料。

Menu Lens research archive · 所有方向都必須接受直接任務比較，而不是靠概念敘述取得通過。
